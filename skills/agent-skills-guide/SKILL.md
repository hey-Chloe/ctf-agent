# Agent Skills 设计与创建指南

帮助用户把可重复的知识或工作流程整理成清晰、可维护、能在适当任务中复用的 Skill。先理解用户要解决的问题，再决定是否需要 Skill；简单说明或一次性任务不必强行包装成 Skill。

## 工作原则

- 将稳定、重复使用的知识和步骤写入 Skill；把易变信息标出来源、版本或核验日期。
- 区分通用格式要求与宿主平台行为。目录发现、自动触发、显式调用和工具能力都可能因平台而异；没有依据时不要承诺自动加载或跨平台完全兼容。
- 让 `description` 同时说明 Skill 的能力和适用时机，使用用户可能说出的具体词语描述触发条件。
- 主文件聚焦执行规则和流程。只有在内容较长、可独立按需阅读时，才拆分到 `references/`；只有能被稳定复用的操作才放入 `scripts/`。
- 对可能访问敏感资料或执行有副作用操作的 Skill，明确权限边界、必要确认、凭证处理和安全检查。
- 不编造业务规则、量化收益、平台命令或能力。将估算明确标成假设，将示例明确标成示例。

## 创建流程

### 1. 明确目标

确认 Skill 服务的用户、要完成的任务、触发场景、输入、输出和边界。若资料不足，先提出最关键的问题；也可以在不影响正确性的前提下，把假设写出来供用户确认。

### 2. 选择最小目录结构

从单文件开始，仅按需要增加资源：

```text
skill-name/
├── SKILL.md
├── references/   # 按需：详细知识、模板、接口说明
├── scripts/      # 按需：可重复运行的辅助程序
└── assets/       # 按需：输出模板或静态资源
```

不要为了显得完整而添加空目录或重复文档。

### 3. 编写元数据

在 `SKILL.md` 开头使用 YAML frontmatter，至少包含 `name` 和 `description`。名称使用小写字母、数字和连字符，并与目录名保持一致。描述简洁具体，既说清功能，也列出常见触发请求。其他字段只有宿主规范支持且确有需要时再添加。

### 4. 编写可执行正文

推荐按任务需要组织为：

- 适用场景与不适用场景
- 所需输入与前置条件
- 执行步骤和关键判断
- 输出格式或交付标准
- 错误处理、权限和安全边界
- 参考资料索引（如有）

写清楚 Agent 如何做事，而不只是罗列主题知识。解释关键约束的原因，避免堆积重复或含糊的“始终/绝不”指令。

### 5. 组织引用和脚本

在 `SKILL.md` 中用相对路径链接 Skill 包内文件。说明何时需要读取每份参考资料；不要假设宿主一定会自动发现嵌套文件。脚本应有清楚的用途、参数、依赖和副作用说明；没有必要时优先提供安全的只读或预览方式。

### 6. 核对与评估

提交前核对：

- frontmatter 可解析，必需字段齐全，名称与目录一致。
- 描述包含明确能力和触发条件，且没有把 Skill 说成自动可用或必然正确。
- 所有相对链接都指向包内存在的文件。
- 示例、内部规范、收益数字和平台命令已标注来源或验证状态。
- 工作流覆盖必要输入、失败处理、输出和权限边界。

用少量真实任务提示验证适用范围和触发描述。对照预期结果检查遗漏、错误触发和不必要步骤；根据反馈改进后再次核对。只有用户明确需要时，才运行工具或脚本进行实际评测，不要声称未执行的测试已经通过。

## 迭代维护

- 从多个真实使用反馈中找共性，再改规则，避免只针对单个提示词打补丁。
- 删除重复、过时或没有帮助的内容；保留能明显改变执行质量的约束。
- 为易变的内部资料注明负责人或权威来源、版本/更新时间和复核方式。
- 更新后重新检查触发描述、文件引用和关键使用场景。

## 面向用户的交付

完成后简要说明 Skill 的用途、触发条件、目录内容、关键假设和未验证的平台特性。若用户要求发布或上传，先确认目标平台与仓库；对写入远端的操作，核实目标路径和文件是否已存在，再执行并报告链接或提交结果。
